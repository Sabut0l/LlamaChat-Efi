# LlamaChat — чат с мини-LLM прямо в UEFI

EFI-приложение (EDK II, `UEFI_APPLICATION`), которое запускает инференс мини-модели
Llama-2 в формате [karpathy/llama2.c](https://github.com/karpathy/llama2.c)
прямо из UEFI, без ОС. Интерфейс поддерживает смешанный ввод и вывод UTF-8
на английском и русском языках.


## Исправления многопоточности

На реальном железе прошивка не обязана передавать AP с готовым FP/SSE-состоянием,
и первый же float на AP давал исключение — AP умирал, а BSP вечно ждал `Ack`
(зависание намертво). Пер-токенный вариант (`MmBeginBatch`/`MmEndBatch`) лечил SSE,
но вызывал `StartupThisAP` на каждый токен и ждал событие завершения AP,
которое прошивка сигналит только по таймеру опроса статуса (~100 мс) — отсюда
дикая просадка скорости.

Текущая схема в `LlamaMp.c`:

- **постоянный пул** — `StartupThisAP` один раз на AP при `MmInit`;
- **явное включение SSE на каждом AP** (`CR0.MP`, сброс `EM`/`TS`, `CR4.OSFXSR`,
  `OSXMMEXCPT`) + FP-самотест до выхода воркера в онлайн;
- **ограниченные ожидания везде**: AP, не вышедший в онлайн за 1 с, исключается;
  watchdog в `MatMul` (2 с) — если воркер перестал отвечать, BSP сам досчитывает
  его срез и навсегда выводит воркера из пула;
- `MmShutdown` тоже с таймаутом (событие зависшего AP намеренно не закрывается).

Итог: в худшем случае приложение деградирует до одного ядра, но **никогда не виснет**.
Диагностика — в debugcon 0x402 (`MmInit: live AP workers`, `MatMul: WATCHDOG ...`).

### Старые прошивки (например AMD E1/Kabini + Aptio 4)

На некоторых старых платах зависают **сами вызовы MP Services внутри прошивки**
(`StartupThisAP`, `GetProcessorInfo` и т.п.) — такой блокирующий вызов из
одноядерного приложения прервать таймаутом невозможно. Для этого случая:

- `MmInit` печатает на консоль каждый шаг (`MP: starting worker on cpu 1` и т.д.) —
  последняя видимая строка перед зависанием называет виноватый вызов прошивки;
- **антизависание `StartupThisAP`**: вокруг каждого вызова взводится сторожевой
  таймер (3 с). Если вызов не вернулся (прошивка вечно ждёт ядро, которое
  не просыпается), колбэк таймера через `SetJump`/`LongJump` выпрыгивает из
  зависшего вызова, MP помечается сломанным (`MP: StartupThisAP HUNG ...`)
  и приложение автоматически продолжает работу в однопотоке. Работает,
  пока прошивка крутится с включёнными прерываниями (типичный случай);
- **аварийный выключатель**: создайте пустой файл `nomp.txt` рядом с
  `LlamaChat.efi` — многопоточность будет полностью пропущена (ни одного
  вызова MP Services), приложение запустится на одном ядре (BSP). Нужен,
  только если даже сторожевой таймер не спасает (прошивка виснет с
  выключенными прерываниями).

## Кириллица в EFI Shell

Вывод кириллицы переведён на метрики OVMF (GraphicsConsoleDxe):

- глиф — фиксированные **8×19** пикселей (`EFI_GLYPH_WIDTH`/`EFI_GLYPH_HEIGHT`),
  без масштабирования; шрифт `LlamaCyrFont.h` перегенерирован в формате
  `EFI_NARROW_GLYPH` (заглавные — строки 4..13, базовая линия — строка 13,
  бит 7 — левый пиксель), как у штатного шрифта прошивки;
- текстовая область **центрирована**: глифы рисуются с учётом полей
  `DeltaX = (HRes - Columns*8)/2`, `DeltaY = (VRes - Rows*19)/2` — ровно так же,
  как GraphicsConsoleDxe размещает собственный текст. Старый код считал ячейку
  как `HRes/Columns × VRes/Rows` от угла (0,0), поэтому кириллица уезжала
  относительно текста прошивки (например, режим 80×25 на 800×600: реальное
  начало текста — (80,62), а не (0,0));
- если геометрия консоли не подходит под 8×19 (нет GOP и т.п.), наложение
  отключается и символы уходят в обычный `OutputString`.
- на время отрисовки глифа аппаратный курсор скрывается (`EnableCursor`):
  GraphicsConsoleDxe «стирает» курсор инверсией пикселей ячейки, и без этого
  под каждой буквой оставалась впечатанная полоса-подчёркивание;
- шрифт перерисован заново в пропорциях штатного шрифта OVMF (LaffStd):
  штрихи 2px, заглавные — строки 4..13, строчные — строки 7..13, единая
  базовая линия на строке 13, выносные элементы (р, у, д, ц, щ, ф) — ниже
  базовой линии, как у латиницы прошивки.

## Состав

```
LlamaChatPkg/
├── LlamaChat.inf      — модуль EDK II (UEFI_APPLICATION)
├── LlamaChat.c        — точка входа: загрузка файлов, чат (модель начинает диалог сама)
├── Llama2.c/h         — порт run.c: трансформер, токенизатор BPE, сэмплер (argmax/temp/top-p)
├── LlamaMp.c/h        — постоянный пул AP-воркеров для параллельного matmul
├── LlamaRuntime.c/h   — CRT-шимы, softfloat-математика (exp/log/sqrt/sin/cos/pow), qsort/bsearch
├── LlamaDebug.c/h     — debugcon 0x402 и файловый журнал
└── LlamaUi.c/h        — текстовая EFI-консоль, UTF-8 и переключение раскладки
```

### Отличия порта от оригинального run.c

- нет `mmap`/`fopen` — чекпойнт и токенизатор читаются целиком через `SimpleFileSystem`;
- нет libm — своя софт-математика (`LmExpf`, `LmSqrtf`, `LmPowf`, `LmSinf`, `LmCosf`);
- нет `qsort`/`bsearch` — свои `LmQsort`/`LmBsearch`;
- нет OpenMP/pthreads — matmul режется по строкам между BSP и AP (MP Services);
- `sscanf("<0x%02hhX>")` заменён ручным парсером `MatchHexByte`;
- `fgets` заменён UTF-8-вводом через `SimpleTextInputEx` (echo + backspace);
- tok/s считается по TSC (примерно, при допущении ~1 ГГц).

## Сборка (EDK II)

1. Скопировать папку `LlamaChatPkg` в дерево EDK II (например рядом с `MdePkg`).
2. Добавить в `[Components]` вашего .dsc (например `MdeModulePkg/MdeModulePkg.dsc` или свой):
   ```
   LlamaChatPkg/LlamaChat.inf
   ```
3. Собрать:
   ```
   build -a X64 -t GCC5 -p MdeModulePkg/MdeModulePkg.dsc -m LlamaChatPkg/LlamaChat.inf
   ```
   (или `-t VS2019` под MSVS — CRT-шимы с `/alternatename` уже подключены).

## Файлы модели

Положить рядом с `LlamaChat.efi` в корень FAT-раздела:

- `model.bin` — чекпойнт llama2.c. Для начала — stories15M (~58 МБ):
  `https://huggingface.co/karpathy/tinyllamas/resolve/main/stories15M.bin` → переименовать в `model.bin`.
- `tokenizer.bin` — из корня репозитория llama2.c.

Нужна chat-модель в формате llama2.c (экспорт через `export.py`), обученная на
схеме Llama-2 chat (`[INST] <<SYS>>...`). Режим генерации историй убран,
stories-модели больше не поддерживаются.

### Форматы model.bin (эта версия, v10)

Поддерживаются **оба** формата экспорта llama2.c, автоопределение по магии файла:

| Формат | Экспорт | Вес модели ~105M параметров |
|---|---|---|
| fp32 legacy (v0) | `python export.py model.bin --checkpoint ckpt.pt` | ~402 МБ |
| **int8 Q8_0 (v2)** | `python export.py model.bin --version 2 --checkpoint ckpt.pt` | **~107 МБ** |

Q8_0 — групповое int8-квантование (по 64 значения на одну fp32-шкалу):
веса лежат в int8, активации квантуются на лету, matmul считается в int8
с fp32-аккумуляцией (порт `runq.c`, параллелится по ядрам как и раньше).
RMSNorm/RoPE/attention/софтмакс — в fp32, потеря качества минимальна.
Бонус: int8-matmul читает в ~4 раза меньше памяти, так что на
memory-bound железе инференс ещё и быстрее.

**Важно:** старые сборки LlamaChat.efi (v9 и раньше) не знают магию `ak42`
и на Q8-файле напишут `implausible config`. Нужна пересборка из этих исходников.

## Запуск в QEMU

```
qemu-system-x86_64 -machine q35 -smp 4 -m 2048 \
  -bios OVMF.fd \
  -drive format=raw,file=fat:rw:hda \
  -debugcon stdio -global isa-debugcon.iobase=0x402
```

где в `hda/` лежат `LlamaChat.efi`, `model.bin`, `tokenizer.bin`.
Дебаг-лог (инициализация MP, загрузка модели, tok/s) пойдёт в stdout через порт 0x402.

## Чат

Выбора режима больше нет: после загрузки модели сразу запускается чат
(до 256 токенов на один ответ, температура 1.0, top-p 0.9). Первый ход делает нейросеть — при
старте ей скрыто подаётся встроенный промпт из `LlamaChat.c`
(`CHAT_SYSTEM_PROMPT` — SYS-персона Злобыча, слово в слово из
`prepare_data.py`, плюс `CHAT_OPENING_PROMPT` — скрытая первая реплика
«пользователя»), и ассистент сам открывает диалог. Дальше — обычный
многоходовый чат по схеме Llama-2 (`[INST] ... [/INST]`), выход — `/exit`.

Число сообщений не ограничено: реализовано скользящее окно контекста.
Когда в окне модели (`seq_len` из `model.bin`, у новой модели — 2048) остаётся
мало места, `Chat()` пересобирает KV-кэш: заново прогоняет SYS-промпт +
последние `HIST_KEEP` (4) обменов и продолжает диалог. В этот момент
выводится служебная строка «[окно контекста заполнено...]» и возможна
небольшая пауза (повторный прогон истории через модель). Старые реплики
за пределами последних 4 обменов модель после пересборки не помнит.
Старая модель с `seq_len=512` тоже работает — просто пересборка будет чаще.

## Русский ввод и вывод

- Отдельного GUI нет: ASCII, переносы строк, прокрутка и курсор обслуживаются
  обычной консолью EFI Shell через `SimpleTextOutput`.
- Для `А–Я`, `а–я`, `Ё/ё` приложение накладывает собственные bitmap-глифы
  9×16 непосредственно в текущую текстовую ячейку через GOP. Рисунок и ширина
  подобраны под моноширинный стиль стандартного шрифта EFI Shell.
- Размер bitmap автоматически подгоняется под фактический размер ячейки,
  вычисленный из текущего текстового режима и разрешения GOP.
- Цвет текста и фона берётся из текущего атрибута `SimpleTextOutput`, поэтому
  кириллица визуально продолжает строку EFI Shell, а не выглядит отдельным GUI.
- UTF-8 от модели потоково преобразуется в Unicode перед выводом.
- `F2` надёжно переключает программную раскладку `EN/RU`; текущий язык показан
  в нижней строке. `Alt` также поддерживается, если прошивка передаёт его через
  `SimpleTextInputEx`. Раскладка русская QWERTY/ЙЦУКЕН.
- Причина, по которой отдельный `Alt` может не работать: UEFI-протокол ввода
  не обязан создавать событие для клавиши-модификатора. На некоторых BIOS
  состояние Alt доступно только вместе с другой обычной клавишей. `F2` имеет
  стандартный UEFI scan code и поэтому не зависит от передачи модификаторов.
- Ввод кодируется в UTF-8, поэтому токенизатор llama2.c получает русские буквы.
  Стандартный `tokenizer.bin` может передать их через byte fallback.
- Понимание русского зависит от самой модели: англоязычная `stories15M` русский
  текст не выучила, даже если интерфейс и токенизатор принимают его. Для чата
  нужна модель, обученная или дообученная на русском и экспортированная в
  совместимый формат llama2.c.

## AMD E1-2500 и MP Services

Причина отличия от Cryptor — вычисления AP в Cryptor целочисленные, а `MatMul`
LLM использует `float`/SSE. На реальной прошивке AP может стартовать с CR0.TS=1
или без включённого OSFXSR; первая SSE-инструкция вызывает исключение, после
чего BSP бесконечно ждёт завершения. QEMU обычно уже подготавливает SSE и поэтому
скрывает проблему.

Перед матричным кодом AP теперь явно очищает CR0.TS/EM и включает CR4.OSFXSR и
OSXMMEXCPT. AP получает только конечные one-shot задачи, как в Cryptor. Чтобы
не запускать AP для каждого `MatMul`, параллельно исполняются только независимые
пары: Q/K и W1/W3; остальные зависимые операции считает BSP.

# Отладочный журнал на реальном железе

Файловый журнал в текущей версии отключён. В `UefiMain` оставлен закомментированный
вызов `DbgInitFile`, который можно вернуть для диагностики. Частые сообщения о
прогрессе чтения каждого мегабайта и индексах токенизатора удалены; краткие
сообщения об успехе и ошибках остаются в debugcon `0x402`.


## Команды модели и конфигурация ПК (LlamaCmd.c)

В чат вшит перехват командных меток, которые модель печатает в ответе
(обучаются через build_commands()/build_sysinfo() в prepare_data.py). Фильтр
`CmdFilter` вырезает метки `<CMD>...</CMD>` из видимого текста и выполняет действие:

- `<CMD>exit</CMD>` — если модель сильно достать/разозлить — она завершает приложение.
- `<CMD>askpass</CMD>` — запрашивает пароль. Следующая строка — пароль, его проверяет
  ПРОГРАММА (в модель не попадает). Верно — `(пароль верный)` + открытие
  `secret.txt`; неверно — `(пароль неверный)`.
- `<CMD>openfile</CMD>` — напрямую открывает `secret.txt` и печатает его.
- `<CMD>sysinfo</CMD>` — приложение собирает конфигурацию ПК и скрытно передаёт
  её модели как `(конфиг: ...)`; модель реагирует по характеру.

### Определение конфига ПК (CmdGatherConfig)

- **CPU** — CPUID 0x80000002..4; **частота** — RDTSC за 50 мс (gBS->Stall);
- **ядра** — MP Services; **ОЗУ** — GetMemoryMap с округлением к типовому объёму;
- **видеокарта** — PCI IO (class 0x03, vendor/device id); **накопитель** — Block IO.

Формат (как build_sysinfo()):
`(конфиг: <CPU>, <X.X> ГГц, <N ядер>, <R> ГБ ОЗУ, <видеокарта>[, накопитель <D> ГБ])`

При `SYSINFO_AUTOSTART 1` (по умолчанию) конфиг передаётся модели автоматически
сразу после приветствия.

### Настройки (LlamaCmd.h)

- `CHAT_PASSWORD` — пароль askpass (по умолчанию `"1234"`).
- `SECRET_FILE` — файл для openfile (`secret.txt`) в корне тома рядом с LlamaChat.efi.

Кириллица в служебных репликах видна только в графическом UI-режиме; в текстовом
режиме EFI печатается только ASCII.

### Сборка

Добавлен файл `LlamaCmd.c` в [Sources] и протоколы `gEfiPciIoProtocolGuid`,
`gEfiBlockIoProtocolGuid` в LlamaChat.inf. Сборка как раньше:
`build -a X64 -t GCC5 -p MdeModulePkg/MdeModulePkg.dsc -m LlamaChatPkg/LlamaChat.inf`
